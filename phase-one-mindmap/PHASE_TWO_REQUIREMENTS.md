# 阶段二追加要求：恢复代次校验

来源：用户在明确授权阶段一时追加“第二阶段补充恢复代次校验，确保备份恢复后网页和 CLI 的旧请求不能重放”。此文件仅记录下一阶段的实施与验收要求，本次不建设后台或 CLI。

## 必须实现的约束

- 权威状态增加 `recoveryEpoch`，使用每次恢复都重新生成、不可复用的代次标识。revision 仍按原计划处理，但不单独承担拒绝恢复前旧请求的职责。可附加单调恢复计数方便展示，计数不是唯一防重放依据。
- 所有网页和 CLI 的写请求都携带当前读取到的 `projectId`、`recoveryEpoch`、`expectedRevision`、`baselineVersion` 和 `operationId`。缺失代次或不同代次均拒绝；没有无需代次的旧协议兼容写入口。
- 在项目锁内，先验证身份和恢复代次，再在**同代次**中查 operationId 回执和版本约束。操作身份为 `(projectId, recoveryEpoch, operationId)`。恢复前的回执可保留历史，但不能导致旧代次请求返回可重放成功或执行新写入；跨代次拒绝优先于原计划的幂等回执逻辑。
- 备份恢复不能照搬备份中的旧代次为当前代次。恢复事务生成新代次、记录来源备份和恢复事件，保全故障文件及上一有效版本。代次与恢复后的有效状态在可靠提交边界一起持久化，不只存于内存、网页或服务会话。重启服务不回退代次；多次恢复同一备份每次都产生新的代次。
- 恢复与并发 CLI/UI 写入串行化：恢复前已提交的动作被记录为可能回退；恢复后的旧请求明确返回 `RECOVERY_GENERATION_MISMATCH`，不写入。若恢复提交结果无法确认，停止写入并重读权威文件，不能猜测当前代次。
- 废弃旧网页会话凭据、未提交审批与待发请求。CLI 同样必须重读；不得自动替换代次、revision 后重放队列，尤其是验收、范围审批和用户决定。网页提示“状态已恢复，请重新读取并重新确认”，CLI 用非零退出码和结构化错误提示。
- 即使损坏文件无法确认 revision 上界，也以新代次隔离旧请求；不得仅重置 revision 或清除幂等记录后继续。恢复请求自身绑定恢复前代次，避免响应丢失后重复恢复再次改变代次；不确定时通过恢复事务记录核对。

## 必测场景

1. 网页和 CLI 在恢复前取得请求，恢复后发送：即使 revision、基线版本恰好一致，也拒绝。
2. 已提交但响应丢失的旧请求，恢复后重试：不跨代次重复执行；明确区分历史回执与当前有效动作。
3. 尚未提交的旧请求复用或改 operationId：仍拒绝；缺失代次也拒绝。
4. 在同一新代次中，重复 operationId 同内容返回原回执，不同内容拒绝。
5. 服务关闭时执行 CLI 恢复，再重启服务：旧网页及旧 CLI 请求仍拒绝。
6. 同一备份连续恢复两次、恢复与写入并发、恢复临时写入或替换阶段中断：不会重新接受旧代次；最后有效状态可识别。
7. 恢复后网页已有审批弹窗失效，不能静默转成针对新状态的审批。

以上保护属于本地受控接口的工作流约束，不宣称能够抵御同一系统用户直接篡改文件。完整方案与故障注入测试待阶段二实施。
